# [L] rind has a constant-time edwards25519 group and ristretto255

## Goal

rind's crate-internal `mid` layer offers ristretto255 (RFC 9496): element encoding and decoding, and the one-way map from 64 uniform bytes, which the OPRF feeds from [hash-to-curve](/quest/m4/protocols/hash-to-curve.md)'s `expand_message_xmd`. Under it sits a constant-time variable-base scalar multiplication on edwards25519, which nothing in rind runs on a secret scalar today: Ed25519 signing multiplies only the base point, and verification's double-scalar multiplication takes public inputs. The [OPRF](/quest/m4/protocols/oprf.md), [FROST](/quest/m4/protocols/frost.md), [ECVRF](/quest/m4/protocols/ecvrf.md), and [OPAQUE](/quest/m4/protocols/opaque.md) quests build on it. No public API: it ships with its first consumer's.

## Plan

- Measure the proven routine first. s2n-bignum's HOL Light-proven `edwards25519_scalarmuldouble`, which rind already copies for verification (`rind/src/mid/ed25519.rs:207`), returns `n * P + m * B`, so a zero `m` gives `n * P` with the whole multiplication inside the proof. Its source selects from both tables in constant time (`thirdparty/s2n-bignum/x86/curve25519/edwards25519_scalarmuldouble.S:663` and `:914`) and it is absent from s2n-bignum's `non_ct_functions.txt`, but its proof states the result, not the timing, so ctgrind must confirm it. rind's AVX2 port of dalek's (`rind/src/low/x86_64/edwards25519_scalarmuldouble_avx2.rs:13`) is variable time and must not serve a secret scalar. Under `AGENTS.md`'s source rule this is the choice unless the ladder below measures more than about 10% faster.
- The alternative: build from s2n-bignum's verified edwards25519 routines (`edwards25519_epadd`, `edwards25519_epdouble`, `edwards25519_pepadd`, `edwards25519_encode`) and field routines (`bignum_invsqrt_p25519`, `bignum_sqrt_p25519`), copied by `admin/parse-asm` like the rest, with a fixed-window ladder over a constant-time table select. The proofs cover each routine; state that the ladder's composition is covered only by tests. Either way RFC 9496's formulas are rind's own, covered only by tests; compare the speed with curve25519-dalek's.
- armv7 and the portable backend have no s2n-bignum: Ed25519 runs curve25519-dalek there (`rind/src/mid/portable/ed25519.rs:3`), so ristretto255 runs dalek's `ristretto` module and its constant-time point multiplication. The differential test against dalek then compares only the assembly backends; on the others the RFC's and Wycheproof's vectors are the check.
- Scalars mod the group order reuse Ed25519's (`bignum_mod_n25519`, `bignum_madd_n25519`), plus a constant-time inversion for the OPRF client's unblinding.
- Test against RFC 9496's Appendix A vectors and the OPRF suite's vectors in RFC 9497, Wycheproof's `ristretto255_scalar_invert_test.json`, differentially against curve25519-dalek as a dev-dependency (aws-lc-rs has no ristretto255), and ctgrind on the scalar multiplication and decoding.
