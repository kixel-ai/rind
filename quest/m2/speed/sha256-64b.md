# [S] x86_64 SHA-256 of 64 B messages as fast as ring

## Goal

SHA-256 of a 64 B message on x86_64 with the SHA extensions matches ring. It reads 1.09-1.19 on the Zen 4 and Zen 5 runners, while rind leads at 32 B and is level from 1200 B.

## Plan

Planned with the maintainer on 2026-11-03 from the speed-gap audit (runs 41552375686, 41550707545, 41550703300, 41522483267).

- Bulk speed is level, so the cost is in finishing the message, not the block function.
- Deferring the last block ([moq-dev/rind#255](https://github.com/moq-dev/rind/pull/255)) is not the cause on its own. Before it, a context already compressed whole blocks from the caller's slice, and trailed ring by more: 1.13-1.24 on Zen 4, 1.23-1.29 on Zen 5. #255 also took Zen 3 from 1.07 to 0.99.
- A context's 64 B message pays either for copying the block (with the deferral) or for the chaining value's trip through memory between two calls (without it). Arrow Lake pays more for the copy: 59 ns deferred, 47 ns not, ring 57 ns. Zen 3 pays more for the trip: 84 ns deferred, 91 ns not, ring 84 ns. The copies' loads fail store forwarding, so the hash waits for older work to retire. `Context::finish(self)` also moves the whole 216 B context.
- [moq-dev/rind#282](https://github.com/moq-dev/rind/pull/282) keeps one call and drops the second copy: the SHA-NI routine takes the padding as a second run of blocks. Its runner benches all drew Zen 3, so Zen 4/5 is unmeasured. On Zen 3, 64 B over ring: main 0.97, #282 0.99 (rind 115.7 vs 115.9 ns), whole blocks compressed in `update` 1.08. #282 landed for its Zen 3 HMAC gains (SHA-256 reused key 64 B 158 to 138 ns, SHA-1 32 B and 64 B about 9% faster); compressing in `update` is ruled out.
- Next: read the 64 B row from the first runner bench of `main` with #282 that draws Zen 4 or Zen 5. If it still trails ring, the remaining suspect is `Context::finish(self)` moving the whole 216 B context, whose stores the finish's loads then wait on. `#[inline]` on `Context::{update, finish}` does not remove the move. Finishing by reference, or wiping and finishing in place, changes ring's signature, so it is an API decision for the maintainer.
- Measure on the Zen 4 and Zen 5 runners, not the local hosts.
