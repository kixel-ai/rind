# [M] Take what rind's upstreams changed since their pins

## Goal

Every upstream rind copies, ports, depends on, tests against, or takes design from is checked for changes since the revision rind pins: security fixes first, then bug fixes, speedups, and newly proven code. Pins whose importer reruns cleanly are bumped in this PR, any security fix is taken outright, and each change that needs a hand port or a design decision is planned as a follow-up.

## Plan

Planned with the maintainer on 2026-11-13: ✅ recurring, every 2 weeks by date (rejected: one run per milestone, first picked, which would stall since m2 and m3 hold outside waits that may never clear; once before each minor release; monthly; quarterly), ✅ in m2 (rejected: m0), ✅ never ends (rejected: at rind 1.0).

So are the upstream test suites the adapters copy, such as rind-ring's, from ring at `2723abbc`. A fix there reaches rind only by porting it, even when Dependabot bumps the crate.
  - Crates: every crate in `Cargo.lock`. Dependabot proposes routine updates of the crates a manifest names, and transitive crates move only when those bumps pull them (maintainer, 2026-11-13: ✅ no lockfile refresh in the run, rejected: `cargo update` with a best-effort cooldown, or with none); the run runs `cargo deny check advisories` over all of them, and takes a flagged transitive fix outright with `cargo update -p <crate> --precise <version>`, or, when the parent's requirement blocks that version, bumps the parent or plans the fix as a follow-up. That is the one exception to no lockfile refresh: a known vulnerability outweighs the cooldown, so only crates cargo-deny flags move, each to its fixed release, plus the parent bump that release needs when its requirement blocks it (maintainer, 2026-11-13: ✅ take flagged transitive fixes, rejected: only report them). The run also reviews what Dependabot skips: majors, and each release that changes the version an adapter tracks, which below 1.0 is major.minor (`sh/adapter-versions.sh`), including rind-ring's, which `package.metadata.rind.upstream` declares without a dependency Dependabot could see. An adapter's is a new `rind-<consumer>` release, planned as a follow-up. A major the run takes itself waits out Dependabot's 7-day cooldown, as the 2026-11-14 run did. It also drops a crate from Dependabot's minor ignores once the adapter's tracked requirement reaches 1.0. A minor release of an adapter upstream from 1.0 on can add API the adapter must mirror; the run leaves that to the adapter API diff (`admin/adapter-api`), which fails the Dependabot PR that brings such a release (maintainer, 2026-11-13: ✅ leave it to the API diff, rejected: the run tracks each adapter's mirrored version by hand).
  - Vectors: `thirdparty/cavp-sha1`, `admin/sync-acvp`, and `admin/sync-vectors`'s sources, Wycheproof, CAVP, and CCTV among them.
  - Design: RustCrypto, libsodium, and ring's library code (rind copies only ring's tests); what they change becomes a follow-up, never a bump.
  - Out of scope: proof tooling and proof projects (Aeneas, Charon, aws-lc-verification, s2n-bignum's new theorems), which [the re-audit](/quest/m4/verified/re-audit.md) surveys; and reporting rind's workarounds, which [upstream-reports](/quest/m2/upstream-reports.md) owns.
- Deliverable (maintainer, 2026-11-13): ✅ bump each pin whose importer reruns cleanly and whose tests, `admin/prove bytes`, and benchmarks hold, and take security fixes outright; plan hand ports and design changes as sized follow-ups (rejected: port everything in the run, which would grow some runs to XL).
